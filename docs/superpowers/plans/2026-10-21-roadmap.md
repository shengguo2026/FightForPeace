# Fight for Peace — Implementation Roadmap to the Stage 1 Vertical Slice

**Status:** Draft for creator review
**Spec:** `2026-10-18-fight-for-peace-game-specification.md` and `Features_Decisions.md` (including §13, review decisions of 2026-10-21)
**Technical basis:** `docs/review/02-technical-evaluation.md`

This roadmap splits the vertical slice into **15 milestones**. Each one ends with something you can run on your own machine (or, when nothing is interactive yet, browser screenshots and a short video from automated tests), plus a checklist of what to try and what feedback I need. Each milestone gets its own detailed task plan, written just before it starts, so that later plans can use what we learn earlier. The first detailed plan (M0) is `2026-10-21-m0-foundations.md`.

## How every milestone is delivered to you

1. I open a pull request on `shengguo2026/FightForPeace` with the milestone's work. CI runs type checks, lint, unit tests, deterministic replay tests and a browser test that captures screenshots.
2. I post a short message with screenshots (and a GIF/WebM for motion), a "What to test" checklist, and the commands to run it locally:
   ```
   git pull
   pnpm install
   pnpm dev        # then open http://localhost:5173
   ```
3. You test and give feedback. I fix what you report, then merge after your approval.

## Placeholder-first asset policy

- From M0 onwards, every visual, audio and video asset is requested through a **logical asset ID** (for example `hero.mountain.pose.idle.01`, `sfx.hit.light.01`, `cine.stage1.intro.shot03`).
- When no approved asset exists, the asset system generates a **placeholder**: a labelled coloured silhouette for characters, flat labelled panels for backgrounds, a tone or click for SFX, and a captioned still card for cinematics.
- When you deliver generated images or clips (all at once or partially), I ingest them into `assets/` with manifest entries, review them at gameplay scale, and the placeholder for that ID disappears automatically. No code changes are needed.
- SFX start from open-source and CC0 sources, and any sound can later be replaced (for example by ElevenLabs output) by dropping in a file with the same logical ID.

**Total:** these milestone estimates add up to about **58–64 weeks (13–15 months)**. That is longer than the 9–13 months in the technical evaluation, because this breakdown includes a test-and-fix round with you after every milestone. If that is too long, the cheapest cuts are moving M12 (local-Wi-Fi) after the slice (saves about 5 weeks) or delivering German and Chinese text at M14 instead of M10. M2–M7 can absorb art batches as soon as you deliver them; nothing in code waits for art.

## Running locally (no hosting)

- Requirements on your Windows machine: **Node.js 24** and **pnpm** (already installed) (one-time install; exact steps are in the README from M0).
- `pnpm dev` serves the game on `http://localhost:5173`. `pnpm build && pnpm preview` serves an optimized local build.
- For LAN co-op (M12), **each computer runs the game locally** and the guest joins the host's room server with its LAN IP, port and room code (see `docs/review/03-network-play-and-licensing.md`).

## Stage 2 guardrails for slice milestones

Stage 2 (`2026-10-24-fight-for-peace-stage-2-specification.md`) is built after the slice, but it is a data-only expansion of the same engine, so a few slice milestones must not hard-code Stage 1 assumptions. None of this adds slice scope; it only constrains how the slice is built. Details are in `docs/review/04-stage2-impact-review.md`.

| Milestone | Guardrail |
|---|---|
| M0 | Replay logs and state encodings carry format and rules versions; tab title is "Fight For Peace". |
| M2 | Heroes are data entries, not code branches; the roster is a list of any length (Stage 2 has four heroes and six legal pairs). Action data keeps open tag sets for outcomes such as `opensGroundWindow`, `terminalKnockdown`, handoff sender/receiver tags and "contact-confirmed conversion" (Fire Warden's catches and clinches). |
| M6 | Weapon state already includes owner, Integrity and finite ammunition per the shared spec, so revolvers, the grenade fuse and the support gun only add data. |
| M7 | Enemy roles and boss phases are data; difficulty substitutions are tables, so Stage 2's Hard/Extreme-only roles need no engine change. |
| M8 | Co-op handoff and team-finisher code is keyed by tags, not by the two founder names, so Reciprocal Handoffs and Twin Guardians' Accord are data. |
| M10 | Profile and save schemas are versioned with migrations, leaving room for Museum, Sponsor Dossier and research-milestone records. Title logos: "Fight For Peace" (EN/DE) and "和平之战" (ZH-CN). |
| M13 | Every Stage 1 picture, clip and music cue keeps a stable logical asset ID, because the Stage 2 Museum indexes Stage 1 media. |

## After the slice: Stage 2 prerequisites

Stage 2's acceptance gate (spec §18) requires all six hero pairs over local Wi-Fi, host-authoritative recovery and host migration. Under D9 those network features (prediction with bounded rollback, survival proxy, host migration) are delivered after the slice, so they become the first post-slice engine milestone, before Stage 2 content work. Stage 2 also debuts the mounted Chase profile, the Preservation Ledger, optional branches and the Museum; these are planned in a separate Stage 2 roadmap when the slice is accepted.

## Out of scope for the slice

Everything needed before selling the game (paid service plans such as Flow Music and Cloudflare, rights and provenance checks, payment, legal and tax items) is tracked in `docs/commercial-release-checklist.md`.

After the creator is satisfied with game quality: online mode (Cloudflare Pages + Workers, WebRTC with online room codes), anti-piracy/licensing (seam: `LicenseAdapter`, always "licensed" in development), and paid-user authentication. Also out of scope: rollback netcode, survival proxy and host migration (after the slice, per D9); Extreme/Ultimate variant art; future heroes; mounts and advanced weapons (schema hooks only); hosting; spoken dialogue.
